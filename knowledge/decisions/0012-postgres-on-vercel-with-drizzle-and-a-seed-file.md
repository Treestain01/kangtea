# 0012 Postgres on Vercel with Drizzle and a seed file

Date: 2026-09-26
Status: Accepted

## Context

The catalogue (store, menu, customisations) lived as TypeScript constants inside `api`, so changing the menu meant a code deploy.
Tristan chose Vercel for the database so it sits next to the api and webapp deployments.
The api must keep working locally and in tests without any database, and agents need repeatable ways to wipe and reseed each environment.

## Decision

Postgres through the Vercel Neon Marketplace integration, accessed with Drizzle ORM over the `pg` driver, with SQL migrations generated by drizzle-kit and committed under `api/drizzle/`.
`seed.json` at the repository root is the single base template for the catalogue and is validated against `@bbt/shared`.
Routes read through a `Catalogue` interface; the Postgres implementation is used when `DATABASE_URL` is set and the seed is served from memory otherwise.
Tests run the real migrations, seed and wipe against PGlite in process.

## Alternatives considered

- Upstash Redis or Vercel KV: fine for a cache, wrong shape for a relational menu that will grow orders, items and options.
- Prisma: heavier client and generated code, slower cold starts on serverless, and a second schema language for one small database.
- Raw SQL with `pg` only: no typed schema or migration diffing, so every schema change would be hand written twice.
- Neon's HTTP serverless driver: faster cold starts, but no transactions over HTTP; the seed relies on one transaction and `pg` works everywhere including the scripts.
- Keeping TypeScript constants and reading them from Postgres later: leaves the deploy-to-change-the-menu problem in place.
- Seeding from TypeScript files: the seed would need compiling to be read by anything other than the api; JSON can be read by any tool and diffed by anyone.

## Consequences

- Menu changes are data changes: edit `seed.json`, test, commit, run the `db-seed` skill per environment. No api deploy is needed.
- `createApp(env, deps)` takes its storage as a parameter, so tests inject the seed catalogue or a fake and never touch the network.
- The seed fallback means a deployment that forgets `DATABASE_URL` still serves the committed menu and logs a warning rather than failing.
- Seeding replaces the catalogue entirely, so hand edits in the Neon console are lost on the next seed. Data that must survive a seed needs its own table and a different loader.
- `api/drizzle/` is generated; Prettier ignores it and agents must not hand edit it.
- PGlite adds a WebAssembly dependency to the api dev dependencies and about a second to the test run.
